# 报告结构

把完整报告写到 `outputs/{ASIN}-penalty-audit.md`。聊天里放结论表和最高优先级代码块。

每条改法都是：**思考**（为什么，可中文）→ **字段名标题** → **代码块（纯原文）**。不要在标题里写“可复制 / 可粘贴”。用户会复制代码块；块内不能有说明。

```markdown
# {ASIN} {站点} 隐性减分体检

## 结论
- 产品一句话、父体、变体表、公开排名/价格
- 品类 overlay（用了哪一节，为什么）
- 1–10 项判定总表（7 核心 + 3 扩展）
- 政策闸门：现行 Seller Central 是否拉到；站点是否 US；有无 warranty / guarantee / 标题字数风险
- Rufus/COSMO 覆盖：谁用、在哪用、箱内有什么、使用边界；空的 discovery 属性；不要把 15 关系或 Q&A 种草写成必改项

## 执行顺序
Day 1 属性/A+ 数字（最安全）
Day 2 非英雄子体标题五点 + Item highlights + ST + 图库 ALT + A+ ALT
Day 3 改图上打架的数字、串色/错配图、徽章图；不动合格主图

## 第 1–10 项
每项先写：判定、证据、思考（哪条官方规则、为什么扣分、服务哪一层：政策 / COSMO / Rufus 可引用 / Lexical）
再写：字段名 + 代码块（纯原文）
没有改法的项（通过 / 英雄标题不动 / 已在做秒杀）不要硬造粘贴块

## 按 ASIN 工单
每个子 ASIN：标题是否改、Item highlights、五点、属性、图库 ALT 槽位表
父体：A+ ALT 全量编号；对比表/FAQ 代码块
ST：通常全变体共用一段

## 待用户补的实测
重量、外箱尺寸、铭牌功率、检测报告、卡尺（若与图上标注不一致则以实测覆盖全文）

## 数据边界
哪些是前台实证，哪些是 DATA_MISSING（尤其第 5 项 ST、第 7 项分不清秒杀与改价、官方帮助页拉失败、非美站点未核实）
```

聊天最少要有：

1. 报告路径
2. 1–10 项判定表
3. 最高优先级粘贴块（通常是统一属性/尺寸、ST、标题策略）
4. 第 4/8 项不通过时：受影响子体的图库 ALT，以及 **A+ ALT**
5. 变体 ≥5 个时，聊天可只放英雄子体 + 问题子体；其余必须在报告文件里给全

完整图库 ALT 和全部 A+ ALT 一律进报告文件，不能只写“稍后补”。
